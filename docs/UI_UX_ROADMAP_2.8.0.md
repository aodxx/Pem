# UI/UX Roadmap — PALM LEDGER 2.8.0

**อัปเดต:** 15 ตุลาคม 2026
**ฐานที่ใช้วางแผน:** Frontend/PWA `2.7.2` (มี Upload Status Indicator), Apps Script `1.3.1`, dashboard รายเดือนและส่งออก CSV/PDF
**หมายเหตุ:** เอกสารนี้สรุปและจัดลำดับข้อเสนอสำหรับรุ่น 2.8.0 โดยอ้างอิงสถานะ production และ flow ที่มีอยู่ใน PALM LEDGER

## เป้าหมายของรุ่น 2.8.0

> **บันทึกบิลหลายใบต่อเนื่องได้เร็วขึ้น โดยรู้สถานะของแต่ละใบ ไม่สลับข้อมูล และไม่ทำให้บิลที่ยังไม่ซิงก์หายไป**

รุ่น 2.7.2 ทำให้สถานะ OCR และการ sync ชัดขึ้นแล้ว รุ่น 2.8.0 ควรต่อยอดจากสถานะระดับ “บิลที่กำลังทำ” ไปเป็น workflow สำหรับผู้ใช้ที่มีบิลหลายใบ พร้อมทำให้การตรวจตัวเลขสำคัญใช้เวลาน้อยลง โดยยังคงให้ผู้ใช้ตรวจและยืนยันก่อนสร้างรายการขายทุกครั้ง

## หลักการออกแบบ

1. **หนึ่งบิล หนึ่งสถานะ หนึ่ง draft** — ห้ามนำรูปหรือค่าจากบิลก่อนหน้ามาปะปนกับบิลถัดไป
2. **แยก “เก็บในเครื่อง”, “กำลังส่ง” และ “บันทึกในชีตแล้ว”** — ห้ามแสดงคำว่าสำเร็จก่อน backend ยืนยัน
3. **ผู้ใช้เป็นผู้ยืนยันรายการขาย** — OCR ช่วยกรอกและชี้จุดผิดปกติ แต่ไม่บันทึกการขายอัตโนมัติ
4. **แสดงความไม่แน่ใจอย่างตรงไปตรงมา** — เน้นเฉพาะช่องที่ควรตรวจ ไม่เดาค่าจากภาพที่อ่านไม่ออก
5. **ออกแบบมือถือและการใช้งานมือเดียวก่อน** — ปุ่มหลักชัด แตะง่าย ไม่มีการเลื่อนแนวนอนหรือ sticky controls บังช่องกรอก
6. **ทำต่อจาก UI และคิวเดิม** — รักษา brand system, idempotency และ offline queue; อย่าสร้าง flow ซ้ำโดยไม่จำเป็น

## ลำดับส่งมอบที่เสนอ

### 0. ปิดการยืนยันบนอุปกรณ์จริงก่อนเริ่มงานใหญ่

เอกสารสถานะโครงการยังระบุการยืนยันบิลจริงบนมือถือสำหรับเวลา `HH:MM:SS` เป็นงานคงค้าง ควรตรวจรุ่น 2.7.2 ด้วยอุปกรณ์จริง รวมถึงทดสอบสถานะ OCR, retry, offline และการบันทึกซ้ำ ก่อนใช้ผลเป็น baseline ของ 2.8.0

### 1. วาง workflow หลายบิล

- หน้าแรกมีทางเข้า “เริ่มชุดบิล” และแสดงรายการในชุด พร้อมเลขลำดับและสถานะ
- แต่ละใบมี draft, รูป, OCR request/idempotency key และสถานะของตัวเอง
- หลังยืนยันบันทึกใบหนึ่งแล้ว ให้เลือก “บันทึกบิลถัดไป” ได้ทันที; ห้ามสร้างรายการขายจาก OCR โดยไม่ผ่านหน้าตรวจและการยืนยัน
- ถ้าใบก่อนยังรอ sync ให้ผู้ใช้ทำใบถัดไปได้ โดยยังเห็นใบก่อนในคิวและไม่แสดงว่าบันทึกลงชีตแล้ว
- จำกัดขนาดชุดหรือจำนวนภาพตามพื้นที่จัดเก็บของอุปกรณ์; แจ้งผู้ใช้ก่อนเกิน quota และห้ามลบ draft เงียบ ๆ

### 2. ทำหน้าตรวจให้เร็วและลดความผิดพลาด

- เปิดด้วย summary ของค่าที่มีผลต่อยอดเงิน โดยไม่ซ่อนค่าที่ต้องแก้
- ช่องที่ไม่มั่นใจหรือขัดกับสมการมี label/ข้อความ ไม่พึ่งสีอย่างเดียว
- เพิ่มการนำทาง “ไปช่องที่ต้องตรวจถัดไป” และสรุปจำนวนข้อที่ยังต้องตรวจ
- ค่าอื่น เช่น หมายเหตุ/รายการหัก/ค่าแรง จัดเป็นส่วนที่ขยายได้ แต่ต้องยังค้นพบและแก้ไขได้
- กรณีที่ validation ไม่ผ่าน ให้บอกสาเหตุและวิธีแก้ ไม่เพียงปิดปุ่มบันทึก

### 3. ทำคิวซิงก์ให้เป็นพื้นที่ทำงานต่อ

- แสดงแต่ละรายการและเหตุผลที่ยังไม่สำเร็จ โดยไม่เปิดเผย Access Token หรือข้อมูลส่วนตัวเกินจำเป็น
- retry ต้องใช้ idempotency เดิม และเมื่อผลจาก server ไม่แน่ชัดต้องตรวจรายการเดิมก่อนสร้างซ้ำ
- ปุ่ม “ลบ” ใช้ได้เฉพาะ draft ที่ยังไม่ส่ง; ห้ามลบรายการขายที่บันทึกแล้วจากหน้าคิวโดยไม่มี flow ยืนยัน/void ที่มี audit trail
- เมื่อ reconnect ให้แสดง “กำลังส่ง” และเปลี่ยนเป็น “บันทึกสำเร็จ” เฉพาะหลังได้รับผลยืนยัน

### 4. เพิ่มตัวช่วยถ่ายภาพเมื่อ P0 เสถียร

เริ่มจาก framing guide และคำแนะนำ ไม่เริ่มจาก auto-dewarp ที่อาจหมุน/ตัดตัวเลขผิด เพิ่มการเตือนเฉพาะเมื่อคุณภาพต่ำจนมีโอกาสอ่านข้อมูลสำคัญไม่ได้ และให้ผู้ใช้เลือกทำต่อหรือถ่ายใหม่ได้

### 5. พิจารณา analytics เป็นงานแยกตามความพร้อมของข้อมูล

อย่าขยายกราฟเพียงเพื่อเพิ่มจำนวนกราฟ ก่อนทำ year-over-year หรือแยกจุดรับซื้อ ให้ตรวจ schema, ความครบถ้วนของวันที่/จุดรับซื้อ และจำนวนตัวอย่างก่อน ค่าเฉลี่ยต้องมีจำนวนบิลและน้ำหนักประกอบเสมอ; ห้ามใช้คำว่า “กำไร” จนกว่าจะบันทึกต้นทุนอื่นครบ

## เกณฑ์รับงานระดับผลิตภัณฑ์

- บันทึกบิล 3 ใบต่อเนื่องได้ โดยแต่ละใบมีรูปและค่าของตัวเอง และผู้ใช้ไม่ต้องกลับหน้าแรกเพื่อเริ่มใหม่
- ปิด/เปิดแอปหรือสลับหน้าแล้ว draft ที่ยังไม่บันทึกกลับมาทำต่อได้ โดยไม่สลับข้อมูลระหว่างบิล
- เมื่อ offline บิลยังแสดงว่าอยู่ในเครื่อง/รอส่ง; เมื่อ online แล้วต้องเห็นสถานะกำลังส่งและผลยืนยันปลายทาง
- การกด retry หรือส่งซ้ำจาก timeout ไม่สร้างแถวขายซ้ำ; ถ้าพบรายการคล้ายกันยังคงให้ผู้ใช้ตรวจและยืนยัน
- ก่อนยืนยันบันทึก ผู้ใช้ตรวจวันที่/เวลา น้ำหนัก ราคา และยอดเงินได้ครบ; ช่องที่ต้องแก้พาไปแก้ได้โดยตรง
- หน้าจอมือถือขนาดเล็กอ่านและกดได้โดยไม่เลื่อนแนวนอน; focus, screen reader status และ reduced motion ไม่ถูกทำให้แย่ลง
- ทดสอบภาพชัด ภาพเอียง/หมุน ภาพซีด/ยับ และกรณีที่ OCR อ่านไม่ได้ โดยระบบไม่เติมตัวเลขที่ไม่มีหลักฐานจากภาพ

## วิธีประเมินผลโดยไม่เก็บข้อมูลเกินจำเป็น

วัดด้วยการทดสอบภารกิจและข้อมูลรวมที่ไม่ระบุตัวตน ไม่เก็บรูปใบชั่งหรือข้อมูลการเงินลง analytics เพิ่มโดยไม่มีเหตุจำเป็น:

- เวลามัธยฐานตั้งแต่เริ่มบันทึกจนจบชุด 3 ใบ
- จำนวนครั้งที่ผู้ใช้ย้อนกลับหรือสับสนว่าใบใดกำลังแก้
- สัดส่วนบิลที่ต้องแก้ฟิลด์สำคัญหลัง OCR และฟิลด์ที่แก้บ่อย
- จำนวนรายการซ้ำ/สูญหาย — เป้าหมายเป็นศูนย์
- จำนวนคิวที่ยังค้างหลังเชื่อมต่อกลับ และเหตุผลที่ต้องให้ผู้ใช้ลงมือแก้

## สิ่งที่ไม่รวมใน 2.8.0

- การบันทึกยอดขายอัตโนมัติโดยไม่มีการตรวจและยืนยัน
- การรับประกันว่า AI อ่านภาพที่ถูกฉีก บัง หรือจางจนไม่มีข้อมูลได้ถูกต้อง
- การพยากรณ์ราคาหรือให้คำแนะนำซื้อ/ขายจากประวัติของสวนเพียงอย่างเดียว
- การเรียกยอดหลังค่าแรงว่า “กำไรสุทธิ” ก่อนมีข้อมูลต้นทุนครบ
- การเพิ่ม analytics/event tracking ที่บันทึกภาพ ชื่อผู้ซื้อ ยอดเงินรายบิล หรือ Access Token

## ข้อเสนอ release cut

ให้ **2.8.0** ส่งมอบ P0 สามส่วน: **ชุดบิลต่อเนื่อง + ตรวจตัวเลขสำคัญ + มองเห็น/กู้คืนคิว** ส่วนตัวช่วยจัดภาพทำได้เมื่อแกนหลักเสถียร; dashboard comparison ควรอยู่ในรุ่นย่อยถัดไปหากข้อมูลหรือ API ยังไม่พร้อม การแบ่งเช่นนี้ช่วยให้รุ่น 2.8.0 แก้ปัญหาการทำงานจริงหนึ่งเรื่องได้ครบ แทนการเปิดหลายฟีเจอร์ที่ยังไม่เชื่อมต่อกัน
